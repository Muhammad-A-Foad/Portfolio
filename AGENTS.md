# AGENTS.md — Portfolio Development Guidelines

## 1. Project Context

This repository contains Muhammad's personal professional portfolio.

Before making content or design decisions, read:

- `PORTFOLIO_BRIEF.md`

Treat this document as the primary source of truth about the portfolio owner.

The website represents Muhammad personally, not Digify Solution or any other organization.

## 2. Professional Positioning

The website must consistently position Muhammad as a:

**Full-Stack Software Engineer**

Backend engineering, databases, architecture, and system design are important strengths, but the overall positioning must remain full-stack.

The website serves two audiences:
1. Recruiters and engineering teams.
2. Potential software clients and business collaborators.

Both audiences should have clear conversion paths.

## 3. Design Standards

Think like a senior product designer and frontend engineer.

- Do not use generic portfolio templates.
- Establish a cohesive visual identity.
- Prioritize typography, spacing, hierarchy, and composition.
- Design mobile-first and ensure desktop layouts are equally polished.
- Use animations purposefully.
- Maintain visual consistency across sections.
- Make project case studies visually engaging.
- Avoid unnecessary visual complexity.

Before implementation, present the proposed design direction and information architecture.

## 4. Engineering Standards

- Write maintainable, readable code.
- Prefer reusable components.
- Use semantic HTML.
- Follow accessibility best practices.
- Optimize images and assets.
- Maintain good performance and SEO.
- Avoid unnecessary dependencies.
- Use TypeScript where appropriate.
- Keep content separate from presentation where practical.
- Handle responsive behavior carefully.
- Do not introduce architectural complexity without justification.

## 5. Content Integrity

Never fabricate:
- Professional achievements.
- Project metrics.
- Users or customers.
- Testimonials.
- Awards.
- Employment history.
- Technical proficiency.
- Project completion status.

Clearly distinguish:
- Personal contributions.
- Team contributions.
- Completed projects.
- Ongoing projects.
- Planned features.

If information is missing, use explicit placeholders or ask Muhammad.

Never invent GitHub repositories, contact details, social links, or external URLs.

## 6. Project Presentation

Projects should be presented as engineering case studies.

Prioritize:
- Problem and business context.
- Requirements.
- Technical decisions.
- Architecture.
- My contribution.
- Engineering challenges.
- Actual outcomes and current status.

Do not reduce projects to screenshots and technology badges.

## 7. Privacy

Do not expose:
- API keys.
- Credentials.
- Internal endpoints.
- Private customer data.
- Confidential business information.
- Unapproved client logos or branding.

Do not publish screenshots without reviewing their contents.

## 8. Development Workflow

Follow this process:

### Phase 1 — Understand
- Inspect the repository.
- Read all relevant project instructions.
- Understand the existing stack and constraints.
- Identify missing assets and information.

### Phase 2 — Plan
- Define the information architecture.
- Establish design direction.
- Identify reusable components.
- Explain the implementation approach.
- Present the plan for approval.

### Phase 3 — Implement
- Build incrementally.
- Maintain consistency with the approved design.
- Avoid unnecessary rewrites.
- Keep components maintainable.
- Ask before making major changes to the agreed direction.

### Phase 4 — Verify
- Run the available build and validation commands.
- Test responsive layouts.
- Check navigation and links.
- Verify accessibility.
- Review performance.
- Check SEO metadata.
- Inspect the final result visually.

### Phase 5 — Report
Summarize:
- What was implemented.
- Important technical decisions.
- Tests performed.
- Remaining issues.
- Missing information or assets.

Do not claim that something was tested unless it was actually tested.

## 9. Independence

Make reasonable technical and design decisions independently.

However, ask Muhammad when decisions require:
- Personal information.
- Missing project details.
- Client permissions.
- External account access.
- Brand assets.
- Professional claims that cannot be verified.

Do not block progress over minor implementation details.
